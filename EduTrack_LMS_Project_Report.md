# ABSTRACT

Modern higher education institutions and universities require comprehensive, integrated software systems to manage academic operations, role-based pedagogical interactions, and statutory governance. Traditional enterprise academic portals often suffer from disconnected modules, insecure direct-editing mechanisms, lack of timely parental communication, and opaque attendance tracking. 

This project presents **EduTrack LMS**, an enterprise-grade academic intelligence and learning operations platform engineered to solve these operational deficiencies. Developed using **React 19, TypeScript, Tailwind CSS v4, Express.js REST API**, and a 3NF normalized **Oracle Database DDL Schema (25 relational tables)**, EduTrack LMS enforces strict **Role-Based Access Control (RBAC)** across four discrete user portals: **University Administrators**, **Faculty Members & Class Teachers**, **Enrolled Students**, and **Parents/Guardians**.

The primary architectural highlights of the system include:
1. **Controlled Profile Management & Multi-Level Approval System:** Replaces hazardous direct CRUD profile editing with an audited state-machine workflow (`Submit Request → Pending Staged Storage → Authorized Review → Atomic Commit`). Institutional identity fields (`student_id`, `reg_number`, `role`, `class_id`, `gpa`) are protected against self-service alterations. Student and parent changes route to the assigned Class Teacher, while faculty changes route to Central Administration. Side-by-side comparison interfaces ensure secure visual verification for profile photographs and personal data.
2. **Two-Stage Onboarding & Registration Pipeline:** Enforces academic verification by the designated Class Teacher (Stage 1) followed by final administrative clearance and credential provisioning by the Central Administrator (Stage 2).
3. **Statutory Attendance Governance & Absence SMS Alerts:** Dynamically enforces the mandatory 75% attendance threshold via a centralized academic calculation engine (`academic.ts`), calculating shortage recovery metrics in real time. Whenever a student is marked absent during class sessions, an automated parent absence SMS alert is dispatched idempotently via an institutional gateway provider abstraction.
4. **Two-Tier Attendance Regularization (Medical Leave & On-Duty OD):** Provides an automated workflow where students submit medical discharge certificates or approved OD documents, timetable sessions are automatically detected, Class Teachers review and endorse requests, and course instructors regularize records to `PRESENT`.
5. **Continuous Internal Assessment & Model Exam Manager:** Facilitates full mark lifecycle management for **IAT-1**, **IAT-2**, and **Model Examinations**, supporting bulk score entry, automatic percentage scoring, and instantaneous publication to student and parent dashboards.
6. **Financial Clearance & Unified Billing Portal:** Generates semester fee invoices with automated dues reminders and simulates multi-channel payment clearance (UPI and Cards) with immediate official tax receipt generation.

The platform was thoroughly verified using automated test suites across all 12 operational domains (41/41 passing test cases) and validated through interactive end-to-end browser sessions across all four stakeholder portals.

**Keywords:** *Learning Management System (LMS), Academic ERP, Role-Based Access Control (RBAC), Controlled Profile Approval, Statutory Attendance Tracking, Automated Absence SMS, Continuous Internal Assessment, Two-Stage Onboarding, React 19, TypeScript, Express.js, Oracle Database.*

# CHAPTER 1 — INTRODUCTION

## 1.1 Background of Academic ERP & Higher Education Systems

In modern educational institutions, digital software platforms form the core nervous system governing academic workflows, institutional governance, communication, and learning delivery. The operational lifecycle of universities requires coordinated interactions among diverse stakeholders: academic administrators managing curricula and faculty allocations, course instructors delivering syllabi and tracking attendance, students submitting coursework and attempting assessments, and parents monitoring student welfare and clearing semester tuition dues.

Historically, academic software environments evolved as isolated, disparate silos. Institutions deployed standalone attendance registers, disconnected billing spreadsheets, third-party learning portals, and separate email distribution channels. This fragmentation created substantial operational friction:
- **Attendance deficits** remained hidden until semester-end examination disqualifications.
- **Student profile alterations** were executed without oversight, allowing unapproved alterations to contact details, legal names, or photographs.
- **Parental involvement** was reactive rather than proactive, frequently lacking real-time insight into ward attendance, internal examination marks, and fee payment status.

To address these systemic challenges, contemporary software engineering emphasizes **unified, secure, multi-role Academic Learning Management Systems (LMS)** backed by strict **Role-Based Access Control (RBAC)**, formal approval workflows, and centralized data governance.

---

## 1.2 Introduction to EduTrack LMS

**EduTrack LMS** is an enterprise-grade university academic intelligence and operations management system designed for universities, engineering colleges, and polytechnic institutes. Engineered around statutory academic compliance and multi-role institutional workflows, EduTrack provides four discrete, personalized user portals:
1. **University Administrator Console:** Oversees institutional users, academic classes, master timetables, fee invoicing, and audit logs.
2. **Faculty & Class Teacher Portal:** Manages course materials, YouTube lecture streaming, real-time session attendance registers, assignment evaluation, timed quizzes, Continuous Internal Assessments (IAT-1, IAT-2, Model Exams), and Class Teacher approval queues.
3. **Student Academic Portal:** Provides unified access to learning materials, coursework submissions, online timed quizzes, live attendance monitoring with statutory 75% shortage calculations, published internal exam report cards, online fee payment with receipt generation, and controlled profile management.
4. **Parent / Guardian Portal:** Scoped strictly to verified wards (`childStudentIds`), providing non-intrusive academic monitoring, attendance shortage alerts, internal assessment gradebooks, fee settlement options, and Class Teacher-mediated profile change tracking.

---

## 1.3 Problem Statement

A critical flaw in traditional academic ERP platforms lies in the **direct CRUD (Create, Read, Update, Delete) editing pattern for user profiles**. In standard implementations, when a student, parent, or faculty member updates their profile information (such as residential address, contact number, or profile photo), the database immediately overwrites the active user record. 

This un-moderated approach introduces severe governance, institutional, and security vulnerabilities:
1. **Unapproved Identity Manipulation:** A student can temporarily update their mobile number or home address to prevent parents from receiving automated absence SMS alerts or institutional notices.
2. **Inappropriate Profile Imagery:** Direct photo uploading permits users to display unverified, informal, or inappropriate avatars across institutional rosters and examination hall tickets before administrative review.
3. **Loss of Audit Continuity:** Direct record mutation without transactional approval destroys the historical audit trail of prior values.
4. **Disrupted Statutory Attendance Tracking:** Disconnected attendance systems fail to provide instant alerts to parents when absences occur, and lack a multi-tier regularization channel for legitimate medical leaves and official On-Duty (OD) representations.
5. **Delayed Assessment Visibility:** Internal assessment marks (IAT-1, IAT-2, and Model Exam) often remain confined to faculty gradebooks rather than being promptly published to students and parents.

Therefore, the problem addressed by this project is to architect, develop, and empirically validate **EduTrack LMS** featuring a **Controlled Profile Management & Multi-Level Approval System** (`Submit Request → Pending Staged Storage → Authorized Review → Atomic Commit`), coupled with an **automated absence SMS alert engine, two-tier attendance regularization (Medical & OD), a historical attendance editor, and continuous internal exam result management**.

- **Streamlined Leave Regularization:** Eliminates manual paper-based medical and OD forms through an automated, multi-tier digital verification pipeline.
- **Holistic Stakeholder Engagement:** Provides parents with dedicated, isolated oversight into their ward's academic trajectory, attendance compliance, exam grades, and fee ledger status.

# CHAPTER 2 — LITERATURE SURVEY

## 2.1 Evolution of Academic Management Systems

Academic management software has evolved across three technological generations:
1. **First-Generation Desktop Database Systems (1990s):** Standalone relational databases (e.g., MS Access, FoxPro) managed by a central registrar. Faculty and students had no direct access; all data entry was centralized and paper-driven.
2. **Second-Generation Web Portals (2000s–2010s):** Web-accessible PHP or Java server applications introducing basic self-service features. However, modules operated in functional silos: learning materials were decoupled from attendance, and parent communication was limited to postal mail or annual grade cards.
3. **Third-Generation Integrated Academic Intelligence Platforms (2020s–Present):** Cloud-native, reactive, single-page applications providing unified real-time operations, strict multi-role RBAC, automated mobile/SMS alerting, continuous evaluation tracking, and governed profile approval workflows.

---

## 2.2 Role-Based Access Control (RBAC) in Academic Environments

Role-Based Access Control (**RBAC**) is defined as an access control mechanism where authorization decisions are determined by the roles assigned to users within an enterprise. In higher education environments, RBAC must enforce contextual boundaries:
- **Separation of Concerns:** Students must not access faculty grading rubrics, examination master keys, or peer attendance summaries.
- **Scoped Data Isolation:** Parents must be strictly restricted to their authorized children (`childStudentIds`). A parent must never view another student's attendance records, fee invoices, or personal details.
- **Course Assignment Governance:** Instructors must only grade assignments and record attendance for courses they are officially assigned to instruct.

---

## 2.3 Attendance Governance & Statutory Compliance

In higher education jurisdictions, accreditation and university statutory regulations mandate a **minimum 75% classroom attendance threshold** as a prerequisite for semester examination eligibility. 

Existing literature indicates that conventional attendance registers fail because:
- Attendance percentage calculations are conducted periodically (e.g., monthly) rather than continuously.
- Students lack immediate feedback on how many consecutive classes are needed to restore compliance.
- Parents are rarely informed of daily absences in real time, preventing timely intervention.

EduTrack LMS resolves this by implementing a dynamic statutory attendance engine that evaluates attendance on every session commit, calculates class shortage recovery counts, and triggers instant parent absence SMS alerts.

---

## 2.4 Profile Integrity & Controlled Approval Workflows

In enterprise software engineering, direct CRUD mutation of master identity records represents a significant architectural risk. 

```
VULNERABLE DIRECT-EDITING PATTERN:
[User Enters New Details] ──► [Direct UPDATE users SET ...] ──► [Unapproved State Active!]

CONTROLLED APPROVAL PATTERN:
[User Enters New Details] ──► [Store in `profile_change_requests`] ──► (Active Profile Unchanged)
                                              │
                                   [Approver Reviews & Signs]
                                              │
                                              ▼
                             [Atomic Transaction: Apply to `users`] ──► [Audit Log Recorded]
```
*Figure 2.1 & 2.2 — Direct-Editing Risk vs. Controlled Approval State Machine*

By isolating proposed changes inside dedicated staging entities (`profile_change_requests`, `profile_change_details`), the active profile continues displaying authorized institutional data while changes await formal review.

---

## 2.5 Continuous Internal Assessment & Exam Evaluation Systems

Under contemporary university assessment frameworks, student evaluation is distributed across Continuous Internal Assessment Tests (**IAT-1**, **IAT-2**) and comprehensive **Model Examinations**. 

Traditional workflows rely on offline spreadsheets, causing delays in marks publication and preventing parents from tracking academic performance. A modern LMS must enable instructors to input marks directly, automatically compute percentage statistics, and publish report cards instantaneously across student and parent portals.

## 2.7 Limitations of Existing Systems

1. **Uncontrolled Profile Alterations:** Existing systems allow users to change their names, contact numbers, and avatars without supervisory clearance.
2. **Delayed Parental Awareness:** Parents are not notified on the day an absence occurs, preventing proactive academic guidance.
3. **Complex Paper-Driven Regularization:** Students must navigate multiple departments to obtain signatures for medical leaves and OD certificates.
4. **Disconnected Financial and Academic Records:** Students cannot view fee invoices and academic report cards in a unified environment.

## 2.8 Research Gap & Problem Formulation

While open-source platforms (e.g., Moodle) excel at course material delivery and commercial ERPs excel at financial accounting, **no unified system seamlessly integrates controlled profile approvals, statutory attendance tracking, instant parent absence SMS alerts, two-tier regularization, internal exam publishing, and multi-channel billing within a modern reactive architecture**. 

EduTrack LMS bridges this gap by delivering an all-in-one, enterprise-grade academic platform tailored for modern institutions.

```typescript
// Controlled Profile Change Request Creation Endpoint
app.post('/api/profile/me/request', (req: Request, res: Response) => {
  const { userId, userRole, changes, pendingAvatarUrl, requestType } = req.body;

  const user = usersStore.find((u) => u.id === userId);
  if (!user) return res.status(404).json({ error: 'User not found' });

  // Enforce Single Pending Request Rule
  const existingPending = profileChangeRequestsStore.find(
    (r) => r.userId === userId && r.status === 'PENDING'
  );
  if (existingPending) {
    return res.status(409).json({ error: 'You already have an active profile change request pending review.' });
  }

  // Validate Field Permissions
  const policyCheck = ProfilePolicyService.validateProfileChange(userRole, changes);
  if (!policyCheck.valid) {
    return res.status(403).json({ error: policyCheck.error });
  }

  // Determine Approval Routing
  let approvalLevel: 'CLASS_TEACHER' | 'ADMIN' = 'ADMIN';
  let targetTeacherId: string | undefined = undefined;

  if (userRole === 'STUDENT' || userRole === 'PARENT') {
    approvalLevel = 'CLASS_TEACHER';
    const academicClass = classesStore.find((c) => c.id === user.classId);
    targetTeacherId = academicClass?.classTeacherId || 'usr-fac-elankavi';
  }

  const newRequest = {
    id: `pcr-${Date.now()}`,
    userId,
    userRole,
    userName: user.name,
    status: 'PENDING',
    approvalLevel,
    classTeacherId: targetTeacherId,
    proposedChanges: Object.entries(changes).map(([key, value]) => ({
      fieldName: key,
      oldValue: (user as any)[key] || '',
      newValue: value
    })),
    currentAvatarUrl: user.avatarUrl,
    pendingAvatarUrl,
    submittedAt: new Date().toISOString()
  };

  profileChangeRequestsStore.unshift(newRequest);
  addAuditLog(user.name, user.role, 'PROFILE_CHANGE_SUBMITTED', `Submitted request ${newRequest.id}`);

  res.status(201).json({ success: true, request: newRequest });
});
```

## 4.5 Controlled Profile Management & Approval Workflow Engine

The profile management architecture enforces strict isolation between active data and pending edits:

```typescript
// Class Teacher: Atomic Approval of Profile Changes
app.post('/api/class-teacher/profile-change-requests/:id/approve', (req: Request, res: Response) => {
  const { id } = req.params;
  const { teacherId, teacherName } = req.body;

  const targetReq = profileChangeRequestsStore.find((r) => r.id === id);
  if (!targetReq || targetReq.status !== 'PENDING') {
    return res.status(409).json({ error: 'Request not found or not in PENDING state.' });
  }

  const targetUser = usersStore.find((u) => u.id === targetReq.userId);
  if (!targetUser) return res.status(404).json({ error: 'Target user record not found.' });

  // ATOMIC COMMIT: Apply all approved proposed changes
  targetReq.proposedChanges.forEach((change: any) => {
    (targetUser as any)[change.fieldName] = change.newValue;
  });

  if (targetReq.pendingAvatarUrl) {
    targetUser.avatarUrl = targetReq.pendingAvatarUrl;
  }

  targetReq.status = 'APPROVED';
  targetReq.reviewedBy = teacherName;
  targetReq.reviewerId = teacherId;
  targetReq.reviewedAt = new Date().toISOString();

  // Audit Logging
  addAuditLog(teacherName, 'FACULTY', 'PROFILE_CHANGE_APPROVED', `Approved request ${id} for ${targetUser.name}`);

  // Push Notification to Student
  notificationsStore.unshift({
    id: `notif-${Date.now()}`,
    userId: targetUser.id,
    title: 'Profile Changes Approved',
    message: 'Your Class Teacher has approved your profile update request.',
    type: 'SYSTEM',
    createdAt: new Date().toISOString(),
    isRead: false
  });

  res.json({ success: true, updatedUser: targetUser, request: targetReq });
});
```

## 4.6 Statutory Attendance, Regularization & SMS Alerting Module

### 1. Calculation Engine (`academic.ts`)
The academic calculation engine computes statutory compliance dynamically:
$$\text{Attendance Percentage} = \left(\frac{\text{Sessions Present}}{\text{Total Sessions}}\right) \times 100$$
$$\text{Shortage Classes Needed} = \max\left(0, \lceil 3 \times \text{Total Sessions} - 4 \times \text{Sessions Present} \rceil\right)$$

### 2. Automated Parent Absence SMS Gateway
Whenever an instructor marks a student `ABSENT`, the server invokes `triggerParentAbsenceSMS`:
```typescript
async function triggerParentAbsenceSMS(attendanceRecord: any, course: any) {
  const student = usersStore.find((u) => u.id === attendanceRecord.studentId);
  const parents = usersStore.filter((u) => u.role === 'PARENT' && u.childStudentIds?.includes(student.id));

  for (const parent of parents) {
    // Idempotency check: prevent duplicate SMS per session
    const existing = smsNotificationsStore.find(
      (s) => s.attendanceId === attendanceRecord.id && s.parentId === parent.id
    );
    if (existing) continue;

    const smsText = `EduTrack Attendance Alert: Your ward, ${student.name}, was marked ABSENT for ${course.title} on ${attendanceRecord.date}.`;
    await smsProvider.sendMessage(parent.phone, smsText);
  }
}
```

# APPENDIX C — VIVA-VOCE & TECHNICAL DEFENSE PREPARATION

### Q1: Why did you implement a Controlled Profile Management system instead of standard direct CRUD editing?
**Answer:** Direct CRUD editing allows students to change contact numbers and addresses immediately without verification. A student could update their mobile number before skipping class to prevent parents from receiving automated absence SMS alerts, or upload inappropriate photos to official exam rosters. The controlled workflow enforces `Submit Request → Pending Staged Storage → Authorized Review → Atomic Commit`, guaranteeing active institutional records remain unchanged until endorsed by the assigned Class Teacher or Administrator.

### Q2: How does the profile approval routing work automatically without user intervention?
**Answer:** The routing is resolved on the server using authenticated database relationships. For a student, the backend determines their `class_id` and looks up the assigned `class_teacher_id` from the `academic_classes` table. For a parent, it looks up their linked child (`childStudentIds[0]`) and routes to that child's Class Teacher. For faculty members, requests route automatically to Central Administration. The user cannot manipulate the approver.

### Q3: How is the statutory 75% attendance rule computed and enforced?
**Answer:** The academic calculation engine (`src/utils/academic.ts`) computes compliance dynamically on every attendance commit:
$$\text{Attendance Rate} = \frac{\text{Sessions Present}}{\text{Total Sessions}} \times 100$$
If the rate falls below 75%, the system renders a statutory `SHORTAGE ALERT` badge and calculates the exact recovery requirement:
$$\text{Classes Needed} = \max\left(0, \lceil 3 \times \text{Total Sessions} - 4 \times \text{Sessions Present} \rceil\right)$$

### Q4: How does the automated parent absence SMS alert maintain idempotency?
**Answer:** When an instructor marks attendance, the backend checks `smsNotificationsStore` for an existing record matching the composite key `(attendanceId, parentId, notificationType)`. If an alert was already queued or sent for that session, duplicate dispatch is blocked, preventing multiple SMS charges and spam.

### Q5: How does the Two-Tier Attendance Regularization workflow operate for Medical and OD requests?
**Answer:** The student submits a request with an uploaded certificate and date range. The server detects all scheduled timetable sessions across that range. In Tier 1, the Class Teacher verifies certificate authenticity and forwards approved sessions. In Tier 2, the respective course faculty endorse the adjustment, and the session attendance status is updated atomically to `PRESENT`.

### Q6: What database architecture supports the EduTrack LMS platform?
**Answer:** The platform is backed by a 3NF normalized Oracle Database DDL schema comprising 25 relational tables (`users`, `academic_classes`, `courses`, `attendance`, `profile_change_requests`, `profile_change_details`, `exam_assessments`, `exam_results`, `fee_records`, `audit_logs`, etc.) with primary keys, foreign key constraints, check constraints, and B-Tree indexes.
